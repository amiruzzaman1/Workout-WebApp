# Workout WebApp: project context for Claude

Personal workout, food and habit tracker. Built for Amir (complete beginner, trains at Jetts Newtown, Wellington NZ) and one friend. Each has their own account and plan. Not published to app stores. Web first; Android/iOS later via Expo Go.

## Stack
- Expo SDK 57, expo-router, React Native Web, TypeScript. Run: `npm run web` (clean cache: `npx expo start --web -c`). Build: `npx expo export --platform web` (output: dist).
- Supabase (auth + Postgres). Project ref `zglxidulxgjfschsrvqm`, URL https://zglxidulxgjfschsrvqm.supabase.co. Client uses the publishable key in `src/lib/supabase.ts`. Never use or commit the service_role key.
- Every table has RLS: `(select auth.uid()) = user_id`, granted to `authenticated` only (automatic table exposure is off). Full schema with versioned sections v1 to v10 in `supabase/schema.sql`; append new changes as a new vN section.
- Hosting: Vercel project `workout-webapp` (vercel.json has SPA rewrite). GitHub repo amiruzzaman1/Workout-WebApp, pushed from GitHub Desktop.
- Shared foods (v10, table shared_foods): foods users add by hand are visible to every signed in user, anyone can edit them, the database records who added and who last edited (trigger), only the creator can delete. The app shows Added or Edited by you or someone else, your own first, with a caution warning on user added foods. Duplicates by name are allowed.
- Data sources: free-exercise-db (public domain images), Open Food Facts (NZ barcodes and search, `src/lib/off.ts`). Typing one or two words first runs a brand search (brandSearch() in off.ts, the newer service's `brands:word*` filter, the last word as a prefix so "collec" already lists The Collective, sold in NZ first), and products whose brand matches what you typed are listed ahead of the rest; Open Food Facts allows about 10 searches a minute, so a brand search that fills the list stops further requests. Search matches each typed word against name, brand, generic name and category (all spellings of yoghurt count as one word, since a real product, The Collective's Epic Greek, is named without "yogurt" and only filed under Greek yogurts); with 3 or more words and fewer than 5 exact matches it also lists products missing one word, and the newer search.openfoodfacts.org service is asked whenever the classic one is down or came up short (it sends brands as a list, not text, and some products there carry only energy-kj_100g, so fromOFF() falls back to kJ divided by 4.184 or those products had 0 calories and were dropped). Every food's energy is written with both units, kcal first and kJ in brackets, "105 kcal (439 kJ)": always print it with fmtEnergy() (or toKJ() for a split layout) in nutrition.ts (KJ_PER_KCAL 4.184), never kcal alone. Used on search rows, the portion screen (with the per 100 values to check against a label), the Food tab total, each meal and logged item, recipes (list, builder, ingredient lines) and the voice command confirm lines; Quick add has a kcal/kJ switch so a label's kJ can be typed directly, still stored as kcal. Scanning (src/components/BarcodeScanner.tsx): web uses the browser's BarcodeDetector (Chrome/Android; iOS Safari falls back to typing the barcode); the Android/iOS app uses expo-camera's CameraView/useCameraPermissions instead, a real native camera module, so the native app always has a working scanner regardless of what the web branch can do (fixed a bug where the native app always showed the "browser can't use the camera" fallback because the supported check was web-only).
- Avoid adding native libraries without telling the user to install them; `react-native-svg` is in package.json and installed, and the Dashboard summary rings use it (LineChart is still plain Views).

- food: index (daily log, macros, water, meal summaries), add (search, scan, my foods, quick add, portion with % of daily targets), nutrition (body stats, BMI, burn breakdown, calorie and macro targets). A food's `unit` is `g`, `ml`, or `piece` (a whole item counted as 1, 2, 3, such as a kebab or a slice, no weight needed); Quick add has a By weight / Whole item choice, and By weight also has a g/ml/kg/L choice for the label's numbers (kg and L are converted down to per 100 g/ml on save, so storage never changes). The Portion screen mirrors this: a piece food asks "How many?" with whole item chips, a weight food keeps its g/ml amount box but can switch to kg/L next to it (the number shown converts, so 500 g becomes 0.5 kg). Sugars and saturated fat are not separate amounts, they are part of carbs and fat (the label's "of which" lines), so Quick add draws each as a smaller, indented `SubField` connected to its Carbs or Fat box with a corner line and labelled "optional", instead of sitting in a plain grid where it would look just as required as the macro above it; fibre and sodium (not part of anything else) stay in the separate "More nutrition" collapsible. `scaleFood()` and `fmtAmount()` in src/lib/nutrition.ts are unit aware; never scale or display a Food or FoodEntry's amount without them. My measures (table food_measures, schema v20; store.tsx's foodMeasures/saveFoodMeasure/deleteFoodMeasure, FoodMeasure and measureKey() in nutrition.ts): on the Portion screen of any g or ml food you can save your own measure ("1 teaspoon = 3 g", name plus how many g/ml one is), kept per food name (lower case, so it follows the food whether found by search, scan or My foods) on your account so it syncs between web and Android. Picking one turns the amount box into "How many teaspoons?" and shows the working ("4 x 3 g = 12 g"); the entry is still saved in plain g or ml, so nothing downstream changes. Not offered for whole item (piece) foods, which are already counted. Delete a measure with its button while it is picked.
- Recipes and usuals (food/recipes.tsx list, food/recipe.tsx builder, table recipes, schema v13): a recipe is a list of ingredient lines (amount in g, ml, tsp, tbsp, cup or piece, NZ measures 5, 15 and 250 ml) with each ingredient's nutrition copied in when saved, so the total (and per serving) is worked out automatically and never changes if a food is edited later. A usual (the milk you always have) is just a one ingredient recipe, made with "Save this amount as my usual" on the portion screen. A recipe becomes a Food through recipeToFood() in src/lib/recipes.ts: per serving as a whole item (unit piece), or per 100 g with a serving size when a cooked weight is entered. Shown first in Search on the add screen, in My foods, and on the Food tab button. Built in lists, bundled offline in src/data and built by scripts/build-food-data.py (not run by the app): ingredients.json (87 curated ingredients from USDA FoodData Central SR Legacy, public domain, with spoon and piece weights so oil, salt and spice calories fill in from a tsp or tbsp), dishes.json (1,014 South Asian dishes from the Indian Nutrient Databank, Jaacks et al., open access CC BY, values per 100 g and per serving), bdfoods.json (379 Bangladeshi foods from the Food Composition Table for Bangladesh, INFS University of Dhaka 2013, via FAO INFOODS; Bengali names are searchable; no sugars or saturated fat in that source), cooked.json (47 everyday cooked foods per 100 g from the same USDA SR Legacy data, including four bone in chicken entries (breast, thigh, drumstick, wings, all with skin) for weighing the cooked piece with the bone still in, since Amir buys bone in chicken: USDA values are for meat without bone and it publishes no bone weight, so those apply an estimated edible share (75, 70, 60 and 50%, from published figures that disagree, stated in each name) to every USDA nutrient, in BONE_IN in the script; built by scripts/build-cooked-foods.py: air fried chicken breast, thigh, drumstick, wings, whole and nuggets, 16 fish and seafood including snapper, king salmon, and a whiting entry searchable as hoki, steak, mince patties, pork chops, bacon, sausage, lamb, turkey, eggs, baked and sweet potato (kumara), frozen chips, tofu. An air fryer uses dry heat and no added oil, so these use USDA's roasted and "cooked, dry heat" entries and oil you add is extra; the script checks every entry's USDA description so a wrong id stops the build. USDA has no roasted skinless drumstick, so that one uses the pan fried meat only entry and reads a little high. Shown as "Air fryer and cooked basics" on the add screen, kept in the order written (breast, thigh, drumstick, wing) rather than by name length, and also found by voice commands and the recipe builder). src/lib/foodData.ts searches them; keep the source credit visible on the add screen.

- Voice commands (Android only, src/components/VoiceCommand.tsx, a floating mic button on the Dashboard): uses expo-speech-recognition, the phone's own on device speech recognizer (no audio leaves the device, no model to download). What it hears is turned into an action by src/lib/voiceParse.ts, plain word matching, not a model, so it never invents an answer; anything it is not confident about comes back as 'unknown' and every match still goes through a confirm screen before it saves anything, with a second, stronger confirm for anything that deletes. "Handle everything" means every action in that file, each a real named thing the app already does, not literally any instruction: start/stop the time tracker or a gym visit, add or delete a task, log or delete a food entry (matched against your own foods, your recipes, and the built in ingredient/dish/Bangladeshi libraries, resolveAmount() converting a spoken amount using the food's own measures), log weight, add/set water, change your goal weight, water goal or fitness goal, and add or delete a daily/weekly/monthly/yearly reminder, log a set for a real exercise (sets, reps, weight or bodyweight, continuing the set numbers if some are already logged today), and going to bed or waking up (reads and writes today's sleep_logs bed_time/wake_time, the same thing the Sleep card's "Bed now"/"Woke now" chips do). The recognizer is given your real food, task, category and reminder names as contextual biasing strings so it mishears them less. src/lib/voiceDictionary.ts remembers what a phrase turned out to mean once you confirm it (this device only), so saying the same food or routine name again resolves straight away instead of being re-guessed; this is the realistic, available today version of "it learns your words", not model fine-tuning, which cannot happen on a phone. A true next step, if ever wanted, is a small on device model (Gemma 3n via Google's MediaPipe LLM Inference API) for phrasing this rule based matching cannot cover, now built (not just a mockup): src/lib/aiAssistant.ts (the model's contract, buildPrompt()/resolveLlmOutput(), which re-grounds every field the model proposes against real data the exact same way a spoken command is, falling back to 'unknown' if a name does not match anything real) and src/lib/aiRuntime.tsx / aiRuntime.android.tsx (the shared AiRuntime, a stub everywhere except Android, where the .android.tsx file Metro picks instead wraps expo-llm-mediapipe's useLLM, Google's MediaPipe LLM Inference API, running Gemma 3n (gemma-3n-E2B-it-int4.task, ~3.1 GB) fully on the phone). Off by default (User settings, app/(tabs)/user/ai.tsx: download, enable, turn off, remove): only asked when the free word matching above has already given up, shown with an 'AI guess' tag, and it still goes through the same confirm-first and delete-twice rules as everything else. VoiceCommand.tsx also has a plain text box next to the mic, for a typed instruction instead of a spoken one; both go through the exact same pipeline. The model's own loading and inference were not testable from this environment (no Android device here); only the surrounding TypeScript was. The native download in expo-llm-mediapipe@0.6.0 has no read timeout, so a connection that stalls after connecting (dead redirect, CDN hiccup, flaky mobile network) hung forever at 0% with no error and no way out; patched via patch-package (patches/expo-llm-mediapipe+0.6.0.patch, postinstall: patch-package in package.json): a 30 second read timeout turns a stall into a catchable error (the existing error UI on app/(tabs)/user/ai.tsx already handles that), and Cancel now actually closes the socket (activeConnections map, connection.disconnect()) instead of only flipping a coroutine flag that a blocked read never checks again. ai.tsx also has a client side watchdog (progress unchanged for 25s) that shows a Cancel button early, before the native timeout would otherwise fire. If the in-app download still will not finish (a flaky connection beats even the 30s timeout repeatedly), app/(tabs)/user/ai.tsx has a manual fallback: "Open the download link" (Linking.openURL(MODEL_URL), the user's own browser downloads the same file, usually far more reliably than this app's downloader) and "Use a file I already downloaded" (ai.importLocalFile() in aiRuntime.android.tsx, expo-file-system's own File.pickFileAsync() system file picker, copied into Paths.document + 'llm_models/' + MODEL_NAME, the exact folder and filename expo-llm-mediapipe's own "already downloaded" check looks at). Since useLLM() only checks disk once, on first mount, aiRuntime.android.tsx wraps the hook in a remountable LlmBridge keyed by a generation counter, bumped after importLocalFile() or remove(), so the runtime notices the file without restarting the app. The mic button (VoiceCommand) is mounted once in app/(tabs)/_layout.tsx, a sibling of the Tabs navigator rather than inside any one tab's own screen, so it floats on every page in every tab, not just the Dashboard. It can also talk back (src/lib/speech.ts, expo-speech, Android's own text to speech, off by default): a speaker icon in the top left of the voice modal (always there, every phase) turns it on or off, persisted the same way as the AI toggle. When it is on, VoiceCommand speaks a short line at the same two moments the modal already changes to show something, understanding a command (speakable(intent), kept in sync with ConfirmCard's own text) and the result (done or the error message), never a running narration of everything typed or heard. Loading an already downloaded model into memory (as opposed to downloading it) had the same silent hang bug as the download once did: the automatic load in aiRuntime.android.tsx's effect caught its own failure and did nothing with it, so a genuine failure (a corrupt or incomplete manually imported file, not enough memory) looked identical to "still loading" forever. Fixed: load failures now set loadError, surfaced on app/(tabs)/user/ai.tsx with a Try again button (ai.retryLoad()); that screen also times how long it has been loading (the first load after a fresh download or a manual import can genuinely take a couple of minutes while MediaPipe sets up its GPU delegate) and says so past 20 seconds, instead of leaving a bare "Loading..." with no sense of whether it is normal or stuck. That error surfacing is what then caught a real, unrelated problem on the real device: Gemma 3n (gemma-3n-E2B-it-int4.task) failed to load with "Unsupported model signature" from odml.infra.LiteRTResourceCalculator, because Google only ever shipped Gemma 3n for the LLM Inference API in the newer .litertlm container, never the Task Bundle (.task) format this library (com.google.mediapipe:tasks-genai, now in maintenance mode) understands, so no download or code fix here could have made that file load. Swapped to Gemma 3, the smaller 1B model, which Google does ship as a real .task file for this exact API (litert-community/Gemma3-1B-IT): MODEL_NAME and MODEL_URL in src/lib/aiAssistant.ts now point at gemma3-1b-it-int4.task (an ungated mirror of that same official file), MODEL_SIZE_MB (560) replacing the old MODEL_SIZE_GB. Getting the model to load was not the end of it: the app crashed outright (not a JS error, the whole process, "it shuts down") the moment a command actually reached the model. maxTokens (the model's whole session budget, prompt and reply together, fixed once at load time) was 256, but aiAssistant.ts's own written contract (systemPrompt()) with a realistic number of foods and exercises filled in comes to roughly 900 tokens on its own, so every real request already overflowed the native engine's buffers before it could even reply, which on this engine is a native crash, not a catchable error. Fixed by raising maxTokens to 2048 in aiRuntime.android.tsx's useLLM() call (the one place it is set, used for both loading and generating since the native session is sized once at creation), with todayTasks and reminders in systemPrompt() now also capped at 30 each (foods and exercises were already capped) so one very full day cannot push it over again.

Also fixed: voice commands for going to bed or waking up ("I woke up at 11:30") were silently ignoring any clock time actually said and always using the current time instead, since the code simply never looked; parseVoiceCommand's sleep_start/sleep_end now call parseTime() on what was heard and only fall back to nowClock() when no time was stated. This needed norm() to stop stripping the colon out of a stated time first, since "11:30" was becoming "11 30" (losing the minutes) before parseTime() ever saw it; colon joins the decimal point in norm()'s allowed characters. The AI model's own sleep_start/sleep_end now accept the same optional time for consistency, though the free word matching above normally catches these phrases first.

More than one action in one sentence ("add a task to call the dentist and start my study timer") now works too, not just the single action each phrase above describes on its own: VoiceIntent has a 'multi' kind ({kind,intents}), and parseVoiceCommand in voiceParse.ts is now a thin wrapper around the original single-command matcher (renamed parseSingle, no longer exported): it tries splitting the sentence on "and then", "then", "and also", then bare "and" (checked in that order so the more specific ones win), and only actually commits to two commands if each half, parsed completely on its own, resolves to something real; otherwise, since one or both halves came back unknown, it is treated as not a real split and the whole sentence is parsed as one command as before. That check is what keeps an "and" that is genuinely part of one phrase ("remind me to call mum and dad", deleting "the eggs and bacon" entry) from being wrongly cut in half: either half alone would be unknown, so the split is rejected. Recurses on the right half so three or more chained actions flatten into one 'multi' rather than nesting. hasDestructive(intent) (also exported from voiceParse.ts) looks inside a 'multi' for the stronger delete confirmation, since isDestructive(kind) alone cannot. In VoiceCommand.tsx, act() loops a 'multi' through itself, speakable() joins each sub-intent's own line, and ConfirmCard's old per-kind body is now IntentBody, reused once per row for a 'multi' (with a thin divider between rows) or once for a single command as before. Also fixed while building this: "add a new task to X" (the word "new") was leaving a stray "to" in the task's title; the add_task pattern now tolerates "new" the same way it already tolerated "a".
- Notifications (src/lib/notify.ts): local reminders, the same small API (notifyNow, scheduleAt, cancelScheduled, startTimerNotification/updateTimerNotification/stopTimerNotification) on web and Android, but genuinely different underneath. Android uses expo-notifications so a reminder still fires with the app closed (needs the Android notification permission, asked once; also needs the user to not battery optimise the app away for it to be reliable). The web has no background scheduler at all, only the browser Notification API plus a setTimeout, so a web reminder only fires while the Forge tab is open somewhere (background tab is fine, a closed tab is not); a closer phone like result there would need a small server sending real push notifications, which this app does not have. Both use an Android notification channel importance HIGH so reminders sort to the top of the panel. The running timer gets its own ongoing notification (useRunningTimer in DayTrackers.tsx starts it, refreshes the elapsed time about once a minute, clears it on Stop). src/lib/dailyNotifications.ts works out and reschedules the day's three check ins (good morning at the wake time, midday, evening, lines in src/lib/dayMessages.ts in the chosen coach's voice) and the three missed log nudges at 12 pm, 6 pm and 12 am (skipped once food is logged and today's tasks are done, unless a day streak is actually running and still not logged today, which keeps them firing and leads with "Don't lose your streak" instead of "Don't forget to log today", since that is a stronger reason to come back); called from the Dashboard every time it mounts, since nothing runs by itself in the background on either platform. Five more situations, each its own function in dailyNotifications.ts, all folded into the one refreshTodayNotifications() call the Dashboard makes: a workout reminder at 6 pm if today has a planned session still untouched; a weigh in nudge (next Monday 9 am) once a week or more has passed since the last one, or there has never been one; a water nudge at 3 pm if well behind pace (scheduled from whatever the percentage was when the app was last open, so like the others it can be stale by 3 pm if nothing changed that in between, the same honest limit the rest of this file already has); a progress photo nudge (next Monday 9:30 am) once two weeks or more have passed since the last one; and a "we miss you" win back nudge for the next morning once the app has gone quiet for 2 or more days (in the coach's own voice, coachStyle.ts). Two more fire immediately rather than on a schedule, the moment they are actually true (src/lib/milestones.ts, checkStreakMilestone/checkGoalMilestone, called from the same Dashboard effect that computes the streak and the coach context): crossing a round number streak (3, 7, 14, 30, 50, 100...) or a quarter/half/three quarters/all the way to the goal weight, each remembered in AsyncStorage so it only ever fires once per crossing, and a changed goal weight quietly resets which thresholds already fired. Several of the nudges (missed log, workout, weigh in, photo) carry real action buttons (src/lib/notify.ts's CATEGORY/ACTION, Notifications.setNotificationCategoryAsync, set up once in initNotifications()) so they can be acted on straight from the notification shade: Log food, Start workout, Log weight, Add a photo, Ask my coach, and a genuine one tap +250 ml water button. Every button still opens the app (Android never hands this app's JS a background tap if the app was fully killed, only if it is still alive in the background, so a button that claims to act without opening the app would silently do nothing on a fully closed app), the water button just also logs the 250 ml the instant the app opens, which is the honest, reliable version of a "one tap" button here. app/_layout.tsx's NotificationActions component (onNotificationAction() in notify.ts, which also checks getLastNotificationResponseAsync() for whatever action cold started the app this time) is what actually runs the tap: navigates for the plain ones, calls store.setWater() directly for the water one. scheduleAt()'s channel and category are two separate, unrelated Android concepts (one picks sound/vibration/importance, the other attaches action buttons); every new nudge above was first wired up passing the category id into the channel slot, which quietly dropped both the buttons and the real channel, caught in review and fixed, now scheduleAt(id, when, title, body, channelId, categoryId) takes both. The progress photo nudge's "Add a photo" button opens /progress?tab=photos rather than just /progress, since Photos is not the default tab there; progress.tsx reads an optional ?tab= param to land on the right one.
- Reminders (table reminders, schema v15, src/lib/reminders.ts, a section on the Tasks page): for things that are not about one day, a daily medicine, a one off future date like cancelling a subscription, or a yearly one like a birthday. nextOccurrence() works out when one is next due from its time, how often, and (for anything but daily) a date whose weekday/day of month/month and day is what actually repeats; refreshReminders() schedules all of them, called from the same Dashboard effect.
- Alarms (table alarms, schema v16, src/lib/alarms.ts, its own page app/(tabs)/tracker/alarms.tsx, reached from a button on the Tracker tab next to the Tasks one): like the phone's own alarm clock, not tied to a day. Once (a date), every day, or certain days of the week (days, an int array, 0 Sunday to 6 Saturday; unlike a Reminder's weekly, which is only ever one fixed weekday); sound and vibration each turn on or off independently, vibration also picks a pattern (short pulse, double pulse, long buzz), and both share one repeat count (1 to 6) for how many times it rings and buzzes. On Android (src/lib/notify.ts) each combination of vibration pattern and sound on or off is its own notification channel, created once in initNotifications(): MAX importance, the phone's ALARM audio stream rather than the notification one (what actually lets it ring through silent mode), bypassDnd (only takes effect once the user has separately granted this app Do Not Disturb access in system settings, nothing here prompts for that). There is no native "repeat this sound and vibration N times" on Android, so scheduleAlarmAt() in notify.ts posts the same notification N times a few seconds apart instead, each one triggering the channel's sound and vibration once on its own; this is also the honest ceiling on how alarm like it gets without a custom native module and a full screen intent, which would also be needed for the stock Clock app's lock screen takeover, so dismissing one here works like dismissing a notification, not silencing a ringing alarm. refreshAlarms() schedules all of them, called from the same Dashboard effect as reminders.

## Key files
- src/lib/store.tsx: all app state and Supabase CRUD (profile, plan, logs, gym visits, food, water, sleep, activities, weights). Logging a newer weight updates profile.weight_kg.
- src/lib/planner.ts: plan generator (splits, two a day, goals incl. recomp), personalised warm ups per session focus, 5 to 9 exercises per session, timed holds.

- src/lib/nutrition.ts: Mifflin St Jeor BMR; burn = BMR x 1.2 + work kcal (weekly hours x job MET x kg / 7) + training kcal; goal weight drives deficit/surplus; recomp 0.4%, muscle 0.5%, fat loss 0.75% bodyweight a week; protein 2.2 g/kg recomp, 2.0 lose, 1.9 muscle, 1.6 general; 1200 kcal floor. Fibre, sugars and saturated fat are calculated the same way as protein/carbs/fat, from your own calorie target (fibre 14 g per 1000 kcal; sugars and saturated fat each capped at 10% of calories, the WHO and NZ Heart Foundation guidance), so they change with your body details and goal. Sodium is a flat 2300 mg population safety limit (NZ Ministry of Health) that does not change with body size. Fibre is a goal (more is good); sugars, saturated fat and sodium are limits (staying under is the healthy range) shown with `limit` on NutrientMini, which flips the colour to A.over past the target. src/components/NutrientMini.tsx is the shared small nutrient readout with a hover bar, used on the Dashboard and the Food tab; both must stay in sync, since the user asked for these to show in both places.
